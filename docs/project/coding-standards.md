# WuwaClone 코딩 규약 초안

- 상태: 사용자 요청으로 dev에 통합하는 초기 규약 문서. 개별 미확정 선택은 사용자 결정 대기로 유지하고, 추가 항목은 콘텐츠 코드 작성 중 사용자 요청에 따라 보완한다.
- 작성일: 2026-10-05 (Asia/Seoul)
- 작업: [Issue #15](https://github.com/soonsoo3595/WuwaClone/issues/15), `codex/15-coding-standards`
- 목적: 첫 이동·카메라 및 데디케이티드 서버 이동 동기화 작업에서 읽기 쉬운 코드와 수명·네트워크 안전성을 확보한다.

## 적용 범위와 기준

| 표시 | 의미 |
| --- | --- |
| 필수 | 최종 채택되면 새 코드와 변경한 코드에서 지켜야 하는 규칙 |
| 권장 | 기본 선택. 다른 선택이 더 적합하면 이유를 설명할 수 있다 |
| 사용자 결정 대기 | 선택지와 제안만 있으며 확정 규칙으로 적용하지 않는다 |
| Epic 기준 | 공식 문서에 있는 관례나 엔진 동작을 요약한 내용 |
| 프로젝트 선택 | WuwaClone에 맞춰 제안한 운영·설계 규칙 |

전체 Epic 규약을 자동으로 의무화하지 않는다. 엔진의 기술적 제약은 스타일 선택과 구분한다. 기존 템플릿·외부 코드는 출처와 권리 표기를 보존하고, 작업과 무관한 일괄 서식 변경이나 이름 변경을 하지 않는다. 확정 이후에도 필요한 변경 범위부터 적용한다.

현재 대상은 UE 게임·데디케이티드 서버의 C++와 Blueprint 경계다. `.Build.cs`·`.Target.cs`는 UnrealBuildTool용 C#으로 기존 UE 관례를 따른다. 향후 Backend·Launcher의 C#에는 UE 타입 접두사나 UObject 규칙을 적용하지 않으며, 해당 영역을 시작할 때 별도 규약을 정한다.

## C++ 스타일과 이름

Epic 기준은 타입 접두사, PascalCase, bool의 `b` 접두사, 탭 들여쓰기와 새 줄 중괄호를 사용한다. [Epic Coding Standard](https://dev.epicgames.com/documentation/en-us/unreal-engine/epic-cplusplus-coding-standard-for-unreal-engine)

- **필수 / Epic 기준 채택 제안:** `A`(Actor), `U`(그 외 UObject), `F`(일반 구조체·타입), `E`(enum), `I`(인터페이스), `T`(템플릿) 등 해당 타입의 UE 접두사를 따른다. UE 인터페이스는 `U` 선언과 `I` 구현을 구분한다.
- **필수 / Epic 기준 채택 제안:** 식별자는 의미가 드러나는 영어 PascalCase로 작성한다. bool 변수는 `bWantsToSprint`, bool 반환 함수는 `CanSprint()`처럼 의미를 드러낸다. 파일명에서는 타입 접두사를 생략한다. 예: `UWuwaMovementComponent` → `WuwaMovementComponent.h`.
- **필수 / Epic 기준 채택 제안:** 탭으로 들여쓰고 표시 폭은 4로 설정한다. 중괄호는 새 줄에 쓰며 한 문장 조건문·반복문에도 생략하지 않는다. `nullptr`, 재정의 함수의 `override`, 읽기 전용 데이터의 `const`를 사용한다.
- **필수 / 프로젝트 선택:** 시간·거리·속도의 단위를 API 주석 또는 이름에서 알 수 있게 한다. 직렬화·복제 데이터는 폭이 명시된 정수형을 사용하고 플랫폼별 크기 가정을 피한다.
- **권장 / 프로젝트 선택:** 호출자가 읽을 공개 인터페이스를 앞에 두고 내부 상태는 기본적으로 private에 둔다. 상속 확장에 필요한 항목만 protected로 노출한다. 의미 있는 기본값을 명시한다.
- **권장 / 프로젝트 선택:** UE API와 연결하는 문자열·컨테이너는 UE 타입을 사용하고, 외부 라이브러리 경계에서 변환한다. 근거 없이 표준 라이브러리 전체를 금지하지 않는다.
- **사용자 결정 대기:** `auto`는 아래 결정 표에서 범위를 정한다. 긴 함수·파일의 숫자 제한, 강제 줄 길이, 멤버 변수의 추가 접두사는 지금 도입하지 않는 것을 제안한다.

## include와 모듈

Epic의 IWYU는 필요한 의존성을 직접 include하고 `.cpp`에서 대응 헤더를 먼저 include하는 방식이다. 게임 프로젝트의 IWYU 설정 변경과 코드 작성 관례 채택은 별개다. [IWYU](https://dev.epicgames.com/documentation/en-us/unreal-engine/include-what-you-use-iwyu-for-unreal-engine-programming)

- **필수 / 엔진 제약:** 리플렉션 헤더의 `*.generated.h`는 마지막 include에 둔다. UHT 대상 선언을 namespace로 감싸지 않는다.
- **필수 / Epic 기준 채택 제안:** 헤더에는 `#pragma once`를 쓰고 자신에게 필요한 선언·정의를 직접 포함한다. `.cpp`는 대응 `.h`를 첫 include로 둔다. 전이 include나 Unity/PCH가 우연히 제공한 선언에 의존하지 않는다.
- **권장 / 프로젝트 선택:** 불완전 타입으로 충분한 포인터·참조 선언에는 전방 선언을 쓰고, 실제 정의는 사용하는 `.cpp`에서 include한다. 상속·값 멤버 등 완전한 타입이 필요한 곳에는 헤더를 포함한다.
- **필수 / 프로젝트 선택:** 새 모듈 의존성은 실제 사용하는 모듈만 `Build.cs`에 선언한다. 공개 헤더의 소비자에게 필요한 의존성은 Public, 구현에만 필요한 것은 Private으로 구분한다. 런타임/서버 모듈이 에디터 전용 모듈에 무조건 의존하지 않게 한다.
- **권장 / 프로젝트 선택:** 새 코드에서 `Engine.h` 같은 거대 헤더를 피한다. 모듈을 미리 잘게 쪼개거나 기존 템플릿의 모듈 의존성을 이번 작업에서 정리하지 않는다.

## UObject 수명과 포인터

공식 문서는 참조의 수명·GC 참여·에셋 로딩 여부에 따라 포인터를 선택하도록 안내한다. `TObjectPtr`만 선언하는 것으로 GC 보호가 생기지는 않는다. [Object Pointers](https://dev.epicgames.com/documentation/en-us/unreal-engine/object-pointers-in-unreal-engine)

| 상태 | 용도 | 제안 |
| --- | --- | --- |
| 필수 / 프로젝트 선택 | 리플렉션 객체 안에서 유지할 강한 UObject 참조 | `UPROPERTY()`와 `TObjectPtr<T>`를 함께 사용 |
| 필수 / 프로젝트 선택 | 수명을 연장하지 않을 관찰·캐시 참조 | `TWeakObjectPtr<T>`, 사용할 때 유효성 확인 |
| 권장 / Epic 안내 | 필요할 때 로드할 에셋·클래스 | `TSoftObjectPtr<T>`·`TSoftClassPtr<T>`, 로딩 실패와 완료 시점 처리 |
| 허용 / Epic 안내 | 함수 인자·반환값·짧은 지역 참조 | `T*`, 호출 동안 수명이 보장되는지 확인 |

- **필수 / 프로젝트 선택:** UObject에는 `new/delete`나 일반 C++용 `TSharedPtr/TUniquePtr`를 소유권 수단으로 사용하지 않는다. 생성 목적에 맞춰 `NewObject`, `SpawnActor`, 생성자의 `CreateDefaultSubobject`를 사용한다. 일반 C++ 객체는 별도 수명 규칙을 따른다.
- **필수 / 프로젝트 선택:** `UPROPERTY` 강한 참조도 Actor의 명시적 파괴를 막는다는 가정은 하지 않는다. 파괴될 수 있는 Actor와 외부 객체는 사용 시점의 `IsValid` 등 적합한 검사로 확인한다. 단순 지역 포인터의 null 검사와 파괴 상태 검사를 구분한다.
- **필수 / 프로젝트 선택:** 지연 콜백·타이머·델리게이트·비동기 작업이 객체 수명을 넘길 수 있으면 약한 참조/바인딩, 취소·해제 또는 명시적 수명 보장 방법을 선택한다. 유효성 검사는 UObject의 임의 스레드 접근을 허용하지 않는다.
- **권장 / 프로젝트 선택:** 소프트 참조의 동기 로딩은 실행 시점과 지연 비용을 고려한다. 비리플렉션 객체에서 UObject를 강하게 유지해야 하는 특수 경우는 GC 참여 방식과 해제 시점을 따로 설명한다.

## Blueprint 경계

- **필수 / 프로젝트 선택:** `BlueprintCallable`, `BlueprintReadOnly`, `EditDefaultsOnly` 등 노출 범위는 사용 목적만큼만 연다. 서버의 권위 상태를 Blueprint나 클라이언트가 임의로 쓰게 하는 접근 경로를 만들지 않는다.
- **필수 / 프로젝트 선택:** PC 입력·Android UI 등 여러 입력 경로가 같은 동작을 요청하면 공통 진입점을 사용해 규칙을 중복하지 않는다. UI나 카메라가 없는 데디케이티드 서버에서도 실행할 수 있도록 표현 기능과 게임 규칙을 구분한다.
- **권장 / 프로젝트 선택:** Blueprint 그래프는 목적별 함수로 나누고 주석으로 의도를 설명한다. 매 프레임 처리는 실제 필요할 때만 추가한다.
- **사용자 결정 대기:** 네트워크 핵심 로직과 Blueprint의 구체적인 분담은 아래 결정 표에서 확정한다. 여기서 특정 클래스 구조나 이동 구현을 확정하지 않는다.

## 오류 처리와 로그

아래 항목은 프로젝트 선택 제안이다. 단정 함수의 정확한 빌드별 동작은 사용하는 엔진 소스·설정에 맞춰 확인한다.

- **필수:** 설정 누락·잘못된 클라이언트 입력·연결 종료처럼 예상 가능한 실패는 검사하고 명시적으로 반환·거부·복구한다. 성공으로 숨기거나 단정 실패로만 처리하지 않는다.
- **필수:** `check`는 개발상 불변식에 사용한다. `ensure`로 이상을 기록하고 계속 진행할 경우에도 실패 경로를 안전하게 처리한다. 검사 매크로 안에 상태 변경이나 반드시 실행해야 하는 코드를 넣지 않는다.
- **필수:** 로그에 비밀번호·토큰·개인정보를 기록하지 않는다. 네트워크 진단에는 대상 객체, 실행 역할/NetMode, 실패 이유 등 필요한 맥락을 남긴다.
- **권장:** 기능별 로그 카테고리를 사용한다. 반복 입력·Tick 로그는 Verbose 수준이나 제한된 진단 옵션으로 제어한다. 화면 디버그 출력만을 서버 진단 수단으로 삼지 않는다.

## 네트워킹·RPC·복제·예측

공식 RPC 문서는 호출 방향·소유 연결과 신뢰성에 따른 실행 조건을 구분한다. Reliable 호출은 전달 확인을 기다리므로 고빈도 입력에 무조건 붙이지 않는다. `WithValidation` 실패는 호출 클라이언트 연결을 종료하므로 정상적으로 발생할 수 있는 요청 거절과 구분한다. [Remote Procedure Calls](https://dev.epicgames.com/documentation/unreal-engine/remote-procedure-calls-in-unreal-engine?lang=en-US)

- **필수 / 프로젝트 선택:** 공유 게임 상태의 최종 판단은 서버에서 수행한다. 클라이언트는 의도를 요청하고 서버는 범위·허용 상태·권한·빈도 등을 실제 요구사항에 맞게 검증한다. `HasAuthority()`와 로컬 입력 소유 여부를 혼동하지 않는다.
- **필수 / 프로젝트 선택:** 각 RPC는 호출자·실행 위치·소유 연결·신뢰성 선택 이유를 설명할 수 있어야 한다. 새 프로젝트 RPC 이름은 `Server...`, `Client...`, `Multicast...`로 방향을 드러내고 UFUNCTION 선언과 일치시킨다. 기존 엔진 API는 이름을 바꾸지 않는다.
- **필수 / 프로젝트 선택:** 재접속·늦게 참가한 클라이언트에도 필요한 지속 상태는 복제 상태로 표현한다. 일회성 이벤트만으로 상태 복원을 대신하지 않는다. RepNotify에서는 재실행·순서 차이를 고려하고 권위 상태 변경과 표현 갱신을 구분한다.
- **필수 / 프로젝트 선택:** Reliable은 전달 보장이 필요한 이벤트에 이유를 갖고 선택한다. Tick마다 Reliable RPC나 위치 Multicast를 추가하는 방식은 기본 이동 구현으로 선택하지 않는다. 다른 Actor의 RPC/프로퍼티 도착 순서를 전역적으로 보장한다고 가정하지 않는다.
- **권장 / 프로젝트 선택:** 첫 캐릭터 이동은 `ACharacter`·`UCharacterMovementComponent`의 기존 예측·서버 검증·보정을 우선 활용한다. 이동에 영향을 주는 새 상태를 추가하면 서버 재현과 보정 후 재생에서 어떻게 유지되는지 설계한다. 별도 예측 시스템을 미리 만들지는 않는다. [Networked Character Movement](https://dev.epicgames.com/documentation/en-us/unreal-engine/understanding-networked-movement-in-the-character-movement-component-for-unreal-engine)
- **필수 / 프로젝트 선택:** 네트워크 변경 설명에는 영향받는 역할(서버·소유 클라이언트·다른 클라이언트)과 검증 결과/미검증 항목을 구분한다. 이 규약 작성은 실행 QA나 특정 복제 시스템(Iris 등)의 채택을 승인한 것이 아니다.

## 주석과 문서

- **필수 / 프로젝트 선택:** API의 비자명한 계약, 단위·범위, 수명, 서버/클라이언트 실행 조건을 설명한다. 코드 내용을 그대로 반복하는 주석은 늘리지 않는다. 동작을 바꾸면 관련 주석도 갱신한다.
- **권장 / 프로젝트 선택:** 클래스·공개 API의 계약은 선언부에, 구현 이유는 구현부에 둔다. `/** ... */`를 필요한 곳에 사용하되 모든 getter·멤버에 형식적인 주석을 강제하지 않는다.
- **권장 / 프로젝트 선택:** 남은 작업의 TODO에는 관련 Issue와 해결 조건을 적는다. 외부 코드의 권리 표기는 유지하며 Epic 표기를 새 프로젝트 자체 코드의 저작권으로 복사하지 않는다.
- **사용자 결정 대기:** Epic은 코드·주석의 영어를 기준으로 한다. 프로젝트 주석 언어는 아래에서 별도로 선택한다. 사용자에게 직접 쓰는 안내와 논의는 현재 사용자 지침에 따라 한국어다.
